# Raspberry Pi 3B+：用户返回重调度的 Release 成本

2026-10-18，真实 Raspberry Pi 3 Model B Plus Rev 1.3、四核、948 MiB firmware
ARM RAM，J-Link RAM 部署；没有写 SD。基线为 `cd9abbf`，原候选为 `24a8975`，
最终候选为 `24a8975` 加本批 `kernel_main.cpp` 的无请求路径判断。

## 改动与边界

第三批接通用户返回的 `check_need_resched()` 后，即使没有请求，也会调用函数并
再次查询当前线程。原候选两轮 raw getpid 的批次中位数均约 0.973 µs，最初基线
为 0.890–0.891 µs；缓存 libc getpid 基本一致。这个观测促使本批检查常见路径的成本。

`user_return_handler` 现在先读取已经取得的线程的 `need_resched`；没有请求时
跳过额外调用。有请求时，调度函数仍重新检查请求、IRQ、抢占计数和 Running 状态，
然后消费请求。标志为假时不清除它，远端随后发布的请求仍可在后续安全点处理。
IRQ 屏蔽的汇编入口、借用 TrapFrame 的生命周期、信号检查顺序和调度函数 API 均沿用。
Release 反汇编确认常见路径为 acquire 读取与分支，跳过重复的 current 查询。

## 受控方法

- 内核使用 Clang 23.1.2、`arm64-release`、`-g0 -Os -DNDEBUG`，
  `MOSS_BUILD_TESTS=ON`、`MOSS_ARM64_PERF_PROBE=OFF`。
- 四次测量启动按“基线、原候选、最终候选、回切基线”排序；每次启动连续两轮。
  同次启动的两轮不是独立冷启动，七个保留批次也不是七次启动。
- 复用现有 `prepare --pmu` 的服务 CPU2 包装，内核 PMU 仍关闭；普通 `measure`
  不带 `--pmu`，不访问 EL0 PMU 或直接 timer 计数器。调用端固定 CPU0，IPC 对端
  固定 CPU0/CPU1，CPU3 仅在每轮前后读温度，计时期间不做 JTAG halt。
- 所有版本使用字节相同的 initramfs、服务和探针。生产 ABI、libc 与探针源码在
  两个原提交间未变，用户态差异仅涉及不进入生产归档的验证程序；各内核保留自身
  构建和符号身份。两个源码目录生成的原生 ELF 字节不同，因此保留原生归档，
  另做共用用户态归档的受控对照。
- 每个场景两个预热批次、七个保留批次，沿用原参数和严格协议：必须收齐样本、
  `RPI_PERF_DONE`、独立的退出状态 0 和下一次 prompt。clock/raw getpid 每批
  20,000 次，libc getpid/yield/IPC 每批 1,000 次，fork/exec 每批 8 次。
- 计时使用生产 `clock_gettime`，各启动日志报告 Generic Timer 为 19.2 MHz。
  表中结果包含探针分派、读取时钟和实际操作的开销，没有扣除未经校准的成本。
  CPU 实际频率及 throttling 状态未采集。

## 观测结果

单位 µs/op；每格为两轮各自的七个批次平均耗时的中位数，**不是单次操作 p99**。
raw fork/libc fork 均包含 wait；exec 包含 fork、BusyBox exec 和 wait；IPC 是往返。

| 负载 | 最初基线 | 原候选 | 最终候选 | 回切基线 |
| --- | ---: | ---: | ---: | ---: |
| clock | 3.978 / 3.938 | 4.044 / 4.044 | 3.968 / 3.964 | 3.981 / 3.938 |
| raw getpid | 0.891 / 0.890 | 0.973 / 0.973 | 0.894 / 0.902 | 0.888 / 0.889 |
| libc getpid | 0.584 / 0.584 | 0.582 / 0.582 | 0.582 / 0.582 | 0.584 / 0.584 |
| yield | 6.517 / 6.529 | 6.619 / 6.657 | 6.570 / 6.649 | 6.506 / 6.581 |
| raw fork + wait | 1080.846 / 1081.029 | 1020.755 / 1008.372 | 1033.607 / 1034.453 | 1064.720 / 1050.104 |
| libc fork + wait | 1859.609 / 1844.414 | 1714.030 / 1753.874 | 1739.050 / 1738.984 | 1823.965 / 1765.208 |
| fork + exec + wait | 9815.697 / 9828.249 | 9564.596 / 9627.669 | 9540.814 / 9613.001 | 9698.926 / 9642.552 |
| 同核 IPC | 118.041 / 118.566 | 98.720 / 96.569 | 98.206 / 98.139 | 115.183 / 115.112 |
| 跨核 IPC | 104.806 / 110.739 | 96.210 / 96.056 | 96.766 / 95.723 | 101.689 / 101.589 |

最终候选 raw getpid 比原候选低约 7–8%，接近最初基线；仍保留与基线的差异。
这与减少常见路径工作的反汇编一致，不能把差值当成某个函数独占的周期数。
yield 等场景未呈现一致收益，不能把本批称作所有系统调用的优化。

回切后 raw getpid 仍接近最初基线，但 fork/exec 变快、同核 IPC 从约 118 降到
115 µs；顺序、温度和调度交错仍会影响组合负载。最终候选 IPC 在这几次启动中
仍较两个基线启动快，fork/exec 的部分差值则明显收窄；没有统计置信区间、
CPU 周期归因或反复交替的多次启动，不能将最初差值全部算作版本收益。
所有轮次前后的温度在 **44.008–46.160°C**。各轮场景的系统切换次数中位数一致：
yield 为 1 次/op、raw fork 为 2、libc fork 为 7.125、exec 为 13.125、IPC 为 2；
它们是区间内全系统计数差，不能当作单线程独占计数。

## 正确性与失败记录

原候选和最终候选的 Release 验证内核分别在 Pi 上通过 users.frame **4/4**，
包含关闭本核 timer 的真实 return_reschedule 交接、寄存器及 FP/NEON 继承检查。
最终候选的三架构 Debug 构建成功，ARM64/x64/RV64 QEMU 各通过 users.frame 4、
scheduler 18、users.ipc 22，共 **132 项**。定向 clang-tidy **1 TU**、clang-format
通过；本批没有修改主机采集器、catalog 或验证用例，也没有重复运行无关主机测试。
这些定向结果不能覆盖第三批 RV64 users.exec 的原始 5 秒超时，其根因仍未确认。

两次候选启动在完整回读并进入 shell 后，默认输入检查只收到相同的
`echo MOSS_RPI_IN` 前缀，均按原 90 秒期限失败。单独发送换行后实际输出
`MOSS_RPI_IN`，证明 shell 当时持有的是截断命令；随后用现有诊断采集器的
500 bytes/s 输入速率重新发送独立 marker，并收到 marker 行和下一次 prompt。
之后普通性能采集的全部命令与协议均通过。原部署结果保持失败，恢复另记，
不能改成一次启动检查通过，也不能由恢复成功宣称 UART 问题已修复。

源码中 UART 字符串输出的 TransmitGuard 持锁、屏蔽本核 IRQ，并等待 TX FIFO；
它是后续接收截断诊断的候选路径。当前没有 overrun 寄存器证据或足够交错实验，
尚未确立丢失位置及其与本次调度改动的因果关系。首次复位因旧 OpenOCD 已关闭
而连接被拒绝，重新附加后正常复位；该主机错误日志也保留。
两次基线启动均通过原输入检查，两次候选启动均出现上述截断；这个启动顺序中的
差别需要继续复现和缩小，不能因采集最终完成而忽略。
